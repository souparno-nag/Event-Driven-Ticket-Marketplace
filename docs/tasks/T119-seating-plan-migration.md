# T119 — The seating plan migration

**What this task did:** wrote `V1__create_seating_plan.sql`, the first of four Flyway migrations for
this service. It creates two tables — `shows` and `show_seats` — and seeds them with exactly the
data the running system needs: nothing more, nothing less.

---

## Why a seating plan has to exist before anything else can

Picture the three ways a booking request can fail that have nothing to do with contention:

1. Nobody has ever heard of this show.
2. The show is real, but "Z99" is not one of its seats.
3. The seats are real, but somebody else already has them.

The third one — contention — is what Redis and the reservation table exist for, and they arrive in
later tasks. But the first two require something to check *against*. Without a table saying which
shows and seat labels are real, this service could never distinguish "that seat doesn't exist" from
"that seat is taken" — and those mean completely different things to a buyer. One will never work no
matter how many times you retry it; the other might work in a minute.

There is no catalogue service anywhere in this project's roadmap that could own this instead. So this
service keeps its own seating plan, and — following the pattern CLAUDE.md and the constitution both
push toward — the only way data enters it is a migration. There is no HTTP endpoint to add a show at
runtime. That is deliberate: the ten-seat pool the step-9 load test contends over needs to be a fixed,
known quantity, not something a stray `curl` command could quietly change.

---

## Two tables, and why they're separate

```sql
CREATE TABLE shows (
    show_id     UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
    name        VARCHAR(200) NOT NULL,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE show_seats (
    show_id     UUID         NOT NULL REFERENCES shows (show_id) ON DELETE CASCADE,
    seat_label  VARCHAR(16)  NOT NULL,
    PRIMARY KEY (show_id, seat_label)
);
```

`show_seats` has no `id` column of its own. Its primary key is the *pair* `(show_id, seat_label)`,
and that is the entire point of the table's shape, not an incidental detail.

Think about what a seat label actually means. "A1" is not a seat — it's a seat *within a particular
show*. The same two characters mean a completely different physical chair in two different venues.
A primary key of `(show_id, seat_label)` encodes that directly: you cannot even ask the question "does
seat A1 exist?" without also saying which show you mean, because the key requires both. That also
makes the existence check this service needs — "do all of these labels exist in this show?" — a single
indexed lookup rather than a table scan, which matters once a booking request is on someone's clock.

One detail worth noticing: `show_id`'s default is `gen_random_uuid()` — generated by the *database*,
not by application code. That is the opposite of how `order-service` generates its order ids (in Java,
before the row exists, so the same value can be used as a Kafka partition key while the transaction is
still open). A show isn't created by a request the way an order is; it's seed data that exists before
any request arrives, so there is no equivalent reason to generate its id anywhere but the database.

## The seed: exactly two shows, and why the count matters

```sql
INSERT INTO shows (name) VALUES ('Load Test Hall');
INSERT INTO shows (name) VALUES ('Second Stage');
```

**"Load Test Hall" carries exactly ten seats** — `A1`–`A5` and `B1`–`B5`. Not nine, not eleven. The
step-9 load test throws 1,000 concurrent booking requests at this exact pool and asserts that *exactly
10* succeed and *exactly 990* are refused. If this seed ever drifted to eleven seats without someone
updating that assertion, the load test would keep passing while testing something subtly different
from what it claims to test — which is a worse outcome than a test that fails loudly.

**"Second Stage" carries three seats, one of which is also called "A1".** That's not carelessness —
it's the whole reason the second show exists. The claim "a seat label is only meaningful relative to
its show" is easy to *state* and easy to get wrong in code that quietly assumes seat labels are
globally unique. Having a second show reuse a label is what makes that assumption testable: a test can
book "A1" in Load Test Hall and "A1" in Second Stage and confirm the system treats them as two entirely
unrelated seats.

**Nothing bigger gets seeded here, on purpose.** The load test's sibling scenarios — 500 overlapping
requests, 500 disjoint requests — need pools of hundreds of seats, and the temptation is to just make
the seed bigger to cover that. This was explicitly rejected during the spec's clarification pass.
Tests that share one big seeded pool interfere with each other unless every single one carefully
carves out its own slice, and a bug that only reproduces depending on which order two unrelated tests
happened to run in is close to the worst kind of bug to chase down. Instead, those tests build their
own throwaway shows and seats for their own exclusive use (`SeatingPlanFixture`, arriving in T140). The
seed stays exactly as large as the *running system* needs — nothing here exists purely to make a test
convenient.

## Verifying it

This SQL was applied directly against a real PostgreSQL 16 instance (the project's own `docker-compose`
Postgres, in a scratch `inventory` schema, torn down afterward) rather than only read for correctness:

```text
INSERT 0 1     -- Load Test Hall
INSERT 0 1     -- Second Stage
INSERT 0 10    -- its ten seats
INSERT 0 3     -- Second Stage's three seats, including the reused 'A1'
```

Querying the result back confirms both the show count and the exact seat count per show match what
the spec requires — ten for Load Test Hall, three for Second Stage — before the schema was dropped
again. No Flyway history was left behind by this check; the real migration run happens when the
application itself boots against these files starting in Phase 2's later tasks.
