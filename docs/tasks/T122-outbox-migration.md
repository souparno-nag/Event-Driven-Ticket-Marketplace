# T122 — The outbox migration

**What this task did:** wrote `V4__create_outbox.sql`, the fourth and final migration for this build
step. It creates `outbox` — the table that lets this service announce a decision (a seat hold granted
or refused) without that announcement ever being lost, duplicated in the wrong order, or silently
skipped.

This table is, on purpose, almost a byte-for-byte copy of the one `order-service` already built in
step 2 (`order-service/src/main/resources/db/migration/V2__create_outbox.sql`). That repetition is
itself a decision worth understanding, not an oversight.

---

## The problem, restated for this service specifically

This service's job, at the moment it decides a booking request, is to do two things: change what it
believes about the world (record a reservation, or don't), and tell everyone else what it decided (send
`seats.reserved` or `seats.rejected` to Kafka). Those are two entirely separate systems — a database
transaction and a message broker — and there is no way to make both of them succeed or fail as one
atomic unit. A database commit and a Kafka send cannot be wrapped in a single transaction together.

So consider what happens if this service tries to do both directly, one after the other: commit the
reservation, *then* publish the message. If the process crashes in the gap between those two steps —
after the commit lands, before the Kafka call completes — the reservation exists, genuinely holding
someone's seats, but nothing downstream has been told. The order sits there forever, waiting for news
that was computed and then lost. Worse: because the idempotency guard (T121) already recorded this
message as processed, a redelivery of the same `order.created` message won't retry the work — it'll
correctly recognize the message as already handled and skip it, which is exactly the right behavior
for a duplicate, and exactly the wrong behavior here, because the announcement genuinely never went
out.

The outbox pattern closes that gap by turning "send a message" into "write a row," which *can* share an
ordinary database transaction with everything else this service decides. `ReservationService` (arriving
in a later task) writes the reservation, the processed-message row, and an outbox row, all in one
transaction. A separate background process — the relay, also already built and just being ported here
— reads pending outbox rows and actually sends them to Kafka, independently and afterward. What's left
to worry about shrinks from "did the reservation and the announcement both happen" down to "the relay
might send the same message twice," which is a problem this project already solved: consumers are
required to be idempotent anyway (that's the entire reason T121 exists).

---

## Why copy the table instead of sharing it

This is the **second** outbox in this codebase — order-service has one, and now inventory-service has
one too, built the same way. The obvious next thought is: shouldn't this be a shared library instead of
two copies of the same schema and the same relay logic?

The project's own constitution has a specific answer to that, and it's worth taking seriously rather
than treating as boilerplate. It requires that any shared abstraction be justified by an *existing,
demonstrated* need — not a hypothetical future one. Two instances of a pattern is exactly the point
where the question "should this be shared?" first becomes visible enough to ask seriously. It is
*not*, on its own, proof that sharing is the right call. A shared module built after seeing exactly two
call sites tends to be shaped by guesswork about what a third caller might need, rather than by
anything actually observed — and guessed-at abstractions are usually wrong in some detail that doesn't
show up until the third caller arrives and has to fight the abstraction rather than use it.

So this table — and the `OutboxRecord`, `OutboxRepository`, and `OutboxRelay` classes arriving in later
tasks — are a deliberate copy, not a shared dependency. If a *third* service someday needs the same
mechanism, that's the moment extraction should genuinely be reconsidered, with two real examples in
hand instead of one. Recording that reasoning here, in the migration itself, means the choice reads as
a decision made on purpose rather than as drift nobody thought about.

## What differs from order-service's version — genuinely almost nothing

Structurally, this table is identical: the same `BIGINT GENERATED BY DEFAULT AS IDENTITY` primary key
with the same caveat about identity order not matching commit order; the same deliberate *absence* of
a foreign key from `aggregate_id` to any parent table (this table is a log of things that must be said,
not a child of the thing it describes); the same `traceparent`/`tracestate` columns carrying trace
context as plain columns rather than folding them into `payload`, so a change in how tracing works can
never force a version bump on the actual message contract; the same two `CHECK` constraints; the same
two partial indexes.

The two things that genuinely differ are what the rows actually *contain*, not the table's shape:

- **`event_type` will hold `seats.reserved` or `seats.rejected`** (from `Topics.SEATS_RESERVED` /
  `Topics.SEATS_REJECTED` in `common-events`, never a hand-typed string) — this service's own two
  outcome messages, rather than order-service's `order.created`.
- **`aggregate_id` can point at an order with *no* corresponding reservation row at all.** Three of
  this service's outcomes are refusals — `SHOW_NOT_FOUND`, `SEATS_NOT_FOUND`, `SEATS_ALREADY_HELD` —
  and none of them create a reservation. The outbox has to be able to announce "your booking was
  refused" for an order this service otherwise has no durable record of ever having tried to hold
  anything for. That's precisely why `aggregate_id` was never a foreign key to begin with, in either
  service's version of this table — a strict foreign key here would make refusals impossible to
  record.

## Verifying it

Applied to a real PostgreSQL 16 instance and then attacked at each of the constraints that give this
table its actual guarantees, not just its shape:

```text
ERROR:  ... violates check constraint "outbox_status_known"        -- status = 'BOGUS' rejected
ERROR:  ... violates check constraint "outbox_published_consistent" -- PUBLISHED with no published_at rejected
ERROR:  ... violates check constraint "outbox_published_consistent" -- PENDING WITH a published_at rejected
```

Both directions of `outbox_published_consistent` were tested, not just one — a row claiming to be
`PUBLISHED` without a `published_at` is rejected, and, just as importantly, a row still `PENDING` that
somehow already has a `published_at` is *also* rejected. That symmetry is the whole point of the
constraint: it exists specifically to stop these two columns, which describe the same underlying fact
from two angles, from silently drifting apart from each other.

A valid insert then succeeded and both partial indexes were confirmed present exactly as specified:

```text
Indexes:
    "outbox_pkey" PRIMARY KEY, btree (id)
    "idx_outbox_parked"  btree (aggregate_id, id) WHERE status::text = 'PARKED'::text
    "idx_outbox_pending" btree (aggregate_id, id) WHERE status::text = 'PENDING'::text
```

All of this ran in a scratch `inventory` schema against the project's own PostgreSQL container, dropped
immediately afterward — no residue left in the shared development database.
