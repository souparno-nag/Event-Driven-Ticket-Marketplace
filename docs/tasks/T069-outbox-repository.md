# T069 — The `OutboxRepository`

**What this task did:** declared a second empty interface, for the outbox table.

```java
public interface OutboxRepository extends JpaRepository<OutboxRecord, Long> {
}
```

---

## Why it is empty when the relay obviously needs a query

The relay's central question is "which records should I send next?", and answering it correctly is
the hardest thing in this build step. That query is **not** here — it arrives in T094, alongside the
relay itself.

The reason it is not written yet is that it cannot be written the easy way. Spring Data's method-name
queries handle things like `findByStatus(OutboxStatus status)`, and that would even look plausible:

```java
List<OutboxRecord> findByStatusOrderById(OutboxStatus status);   // wrong, in a subtle way
```

Run two copies of the service and both relays get the same rows, and both send them. The query
needs to **claim** rows — take an exclusive lock so no other relay can see them — and to skip rows
another relay already holds rather than waiting behind them. It also has to guarantee that messages
for one order go out in the order they were recorded, which needs a correlated subquery.

None of that is expressible as a method name. It will be a hand-written native SQL query using
`FOR UPDATE SKIP LOCKED`, which is precisely the kind of thing SQL is good at and an ORM is not.

---

## `Long`, not `UUID`

`OrderRepository` is keyed by `UUID` and this one by `Long`. That is not an oversight.

An order's identifier only needs to be unique, and a UUID can be generated by the application
without asking the database — which is exactly why it was chosen.

An outbox record's identifier needs something more: it has to define an **order**. It records the
sequence messages were written in, and that is the sequence they must be published in. A monotonic
number carries that. A random UUID carries none of it, and sorting by one would produce a shuffle.
