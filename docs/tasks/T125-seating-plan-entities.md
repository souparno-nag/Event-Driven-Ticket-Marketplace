# T125 — The seating plan entities

**What this task did:** wrote the Java side of the seating plan migration from T119 — `Show`,
`ShowSeat`, `ShowSeatId`, and `SeatingPlanRepository`. Together these let application code ask the two
questions the seed data exists to answer: does this show exist, and do these seat labels exist within
it?

---

## Entities that the application never creates

Every entity written so far elsewhere in this project — `order-service`'s `Order`, and this service's
own `Reservation` (T126) — gets created by application code responding to a request. `Show` and
`ShowSeat` are different in a way worth naming explicitly: **nothing in this service's Java code ever
calls `save()` on either of them.** Every row exists because `V1__create_seating_plan.sql` put it
there at migration time, and stays that way because there's deliberately no HTTP endpoint anywhere in
this service that could create a new one. That's a real design decision, not an oversight — it means
the ten-seat pool the load test depends on can't be changed by a stray request; changing it means
writing a new migration.

That read-only nature actually simplifies `Show`:

```java
@Id
@Column(name = "show_id")
private UUID showId;
```

No `@GeneratedValue`. The database's own `DEFAULT gen_random_uuid()` assigns this value once, at seed
time — and because Hibernate never *inserts* a `Show` row, it never needs to read a generated value
back from one. Compare this to `Reservation` (T126), where the id genuinely is decided by application
code before the row exists, for a concrete downstream reason.

## Why a seat label needs two fields to mean anything

`show_seats`' primary key, from T119, is the pair `(show_id, seat_label)` — no surrogate `id` column
of its own. Modeling that pair in JPA needs somewhere for those two fields to live together as one
identity, and JPA gives you basically one clean way to do that for a *value*-shaped composite key:
`@EmbeddedId`, backed by a small class annotated `@Embeddable`.

```java
@Embeddable
public class ShowSeatId implements Serializable {
    private UUID showId;
    private String seatLabel;
    // equals/hashCode by both fields, hand-written
}
```

Why hand-written `equals`/`hashCode` here, when this project has been careful elsewhere to avoid
Lombok generating exactly that for an entity? The two situations aren't actually the same risk. The
danger with an entity like `Order` is that its identity is a database-generated value that doesn't
exist yet when the object is first constructed — a Lombok-generated `hashCode()` there would change
the moment the object is saved, silently corrupting any `HashSet` already holding it. `ShowSeatId` has
no such problem: both of its fields are decided at construction and never change afterward, because
they're never generated by anything — they're copied straight out of the seed data. A composite
`@EmbeddedId` class is specifically required by the JPA spec to implement `equals`/`hashCode` based on
its field values, and there's no window here where those values could be unstable.

`ShowSeat` itself, then, is almost nothing:

```java
@EmbeddedId
private ShowSeatId id;
```

One thing it deliberately doesn't have: any `@ManyToOne` link back to `Show`. Nothing in this service
ever walks from a seat to its show as an object graph — every actual use is "does this exact
`(showId, seatLabel)` pair exist", which the id class already answers completely on its own. Adding a
relationship here would be exactly the kind of speculative structure the project's own constitution
argues against — built for a navigation pattern nothing in the code actually performs.

## One repository for two entities — and why that isn't sloppy

`SeatingPlanRepository extends JpaRepository<Show, UUID>` gets "does this show exist" for free, via
the inherited `existsById`. The seat-label question needs its own method:

```java
@Query("""
        SELECT ss.id.seatLabel
        FROM   ShowSeat ss
        WHERE  ss.id.showId = :showId
          AND  ss.id.seatLabel IN :seatLabels
        """)
Set<String> findExistingSeatLabels(UUID showId, Collection<String> seatLabels);
```

This is the "one query rather than N" the task asked for — a single round trip that checks every
requested label at once, rather than looping and asking about one seat at a time. The caller compares
the size of what comes back to the size of what was asked for: if they match, every label is real; if
they don't, at least one isn't, and the request gets refused with `SEATS_NOT_FOUND`.

The repository interface is typed to `Show`, but this query reads `ShowSeat` — a different entity
entirely. That's allowed (Spring Data doesn't require a `@Query` method to stay within its interface's
own generic type), and it's deliberate here rather than incidental: `Show` and `ShowSeat` are two
tables that exist to answer one conceptual question together — "is this booking request even asking
for something real?" — and there is exactly one caller in this entire service that ever asks either
half of it. Splitting this into a `ShowRepository` and a separate `ShowSeatRepository` would scatter
one check across two files, for a distinction nothing in the code actually needs.

## Verifying it

These four files, together with T126–T129's, were verified as a group by writing a temporary
Spring Boot test that booted the *real* application context against a live PostgreSQL 16 database
(the project's own container) with Flyway migrating a clean `inventory` schema first. That test:

- confirmed `SeatingPlanRepository.findAll()` finds the seeded "Load Test Hall" show, with a real,
  database-assigned `showId`;
- confirmed `findExistingSeatLabels(showId, Set.of("A1", "A2", "Z99"))` returns exactly `{A1, A2}` —
  correctly finding the two real labels and correctly omitting the fabricated one, in one query.

The test file itself was temporary and has been removed — the durable test infrastructure for this
service (`InventoryIT`, `InventoryKafkaIT`) arrives in T138 and T139, and building it early would be
scope the current tasks didn't ask for. What the smoke test caught in the meantime — a schema
configuration bug from T117 that would otherwise have surfaced as a mysterious "missing table" the
first time *any* entity in this service was actually used — is recorded as its own correction commit.
