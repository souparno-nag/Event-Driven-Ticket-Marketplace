# Phase 1 Data Model: Order Acceptance & the Transactional Outbox

**Feature**: `002-order-service-outbox` | **Date**: 2026-08-23

Two tables in one PostgreSQL schema owned solely by `order-service`. No other service reads or
writes them; everything they need travels as messages. Design decisions referenced as **R*n*** come
from [research.md](./research.md).

---

## Entity relationship

```text
        orders                          outbox
    ┌──────────────────┐            ┌─────────────────────┐
    │ id          (PK) │◄───────────│ aggregate_id        │   no FK constraint — see below
    │ user_id          │  logical   │ id            (PK)  │   BIGINT identity: recording order
    │ show_id          │            │ event_type          │
    │ amount           │            │ payload      jsonb  │
    │ status           │            │ traceparent         │
    │ version          │            │ tracestate          │
    │ created_at       │            │ status              │
    │ updated_at       │            │ attempts            │
    └────────┬─────────┘            │ last_error          │
             │ 1..n                 │ created_at          │
    ┌────────▼─────────┐            │ published_at        │
    │ order_seats      │            └─────────────────────┘
    │ order_id   (FK)  │
    │ seat_id          │
    │ PK(order_id,seat)│
    └──────────────────┘
```

**Why `outbox.aggregate_id` carries no foreign key.** The outbox is a log of things that must be
said, not a child of the order. A foreign key would make deleting or archiving an order require
deciding what happens to messages already sent about it, and would block a future step from
recording a message about anything that is not an order. The column is documented as referring to
`orders.id`; the database is not asked to enforce it. **TRADEOFF**: a typo in application code could
write an unmatched `aggregate_id` and no constraint would catch it. Accepted because the only writer
is the same `@Transactional` method that creates the order, and it uses the order object it just
built.

## Table: `orders`

Migration `V1__create_orders.sql`.

```sql
CREATE TABLE orders (
    id          UUID           PRIMARY KEY,
    user_id     UUID           NOT NULL,
    show_id     UUID           NOT NULL,
    amount      NUMERIC(19,2)  NOT NULL,
    status      VARCHAR(16)    NOT NULL,
    version     BIGINT         NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ    NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ    NOT NULL DEFAULT now(),

    CONSTRAINT orders_status_known CHECK (status IN ('PENDING', 'CONFIRMED', 'CANCELLED')),
    CONSTRAINT orders_amount_non_negative CHECK (amount >= 0)
);

CREATE TABLE order_seats (
    order_id  UUID         NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
    seat_id   VARCHAR(32)  NOT NULL,
    PRIMARY KEY (order_id, seat_id)
);
```

| Column | Type | Serves | Notes |
|---|---|---|---|
| `id` | UUID | FR-003 | Also the saga id and the Kafka partition key. Generated by the application, not the database, so the id exists before the row does and can be returned even if the write fails. |
| `user_id` | UUID | FR-001 | Taken on trust; no authentication until step 7. |
| `show_id` | UUID | FR-001 | Named `show_id`, never `event_id` — step 1 renamed this precisely because it collided with message identity. |
| `amount` | NUMERIC(19,2) | FR-005 | Exact decimal, scale fixed at 2. Never `float` or `double`: the step-9 load test and the simulated decline rule both compare amounts exactly. |
| `status` | VARCHAR(16) + CHECK | FR-004 | All three states are declared now; only `PENDING` is reachable in this step. Declaring them costs nothing and avoids a migration in step 4. |
| `version` | BIGINT | FR-022 | JPA `@Version`. Present now, exercised by a conflict test; retry logic deferred — R9. |
| `created_at` / `updated_at` | TIMESTAMPTZ | diagnosis | Always `TIMESTAMPTZ`, never `TIMESTAMP`: a naive timestamp silently means a different instant in another zone. |

**Why seats live in a child table** rather than a `text[]` column or a JSON blob: the composite
primary key makes duplicate seats on one order impossible *in the database*, which turns FR-005's
"reject a duplicate-containing seat list" from a validation rule that could be bypassed into an
invariant that cannot. It also maps to plain JPA `@ElementCollection` with no custom Hibernate type.
**TRADEOFF**: one join to read an order. Negligible against a single-order lookup, and the alternative
buys nothing this system needs.

### State machine

```text
                    ┌──────────────────────────────┐
   POST /api/orders │                              │
   ────────────────►│           PENDING            │
                    └──────┬───────────────┬───────┘
                           │               │
       PaymentSucceeded    │               │  SeatsRejected | PaymentFailed
            (step 4)       │               │       (step 5)
                           ▼               ▼
                    ┌────────────┐   ┌────────────┐
                    │ CONFIRMED  │   │ CANCELLED  │      both terminal
                    └────────────┘   └────────────┘
```

In this step only the entry arrow exists. Both transitions out of `PENDING` are built in later steps
and are the reason `version` is needed.

## Table: `outbox`

Migration `V2__create_outbox.sql`.

```sql
CREATE TABLE outbox (
    id            BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    aggregate_id  UUID         NOT NULL,
    event_type    VARCHAR(64)  NOT NULL,
    payload       JSONB        NOT NULL,
    traceparent   VARCHAR(64),
    tracestate    VARCHAR(512),
    status        VARCHAR(16)  NOT NULL DEFAULT 'PENDING',
    attempts      INTEGER      NOT NULL DEFAULT 0,
    last_error    TEXT,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    published_at  TIMESTAMPTZ,

    CONSTRAINT outbox_status_known CHECK (status IN ('PENDING', 'PUBLISHED', 'PARKED')),
    CONSTRAINT outbox_published_consistent
        CHECK ((status = 'PUBLISHED') = (published_at IS NOT NULL))
);

-- Serves the claim query's main scan AND its MIN(id) subquery (R2). Partial, so it indexes only
-- outstanding work: once a row is published it leaves the index entirely, which is what keeps the
-- relay's cost proportional to the backlog rather than to the table.
CREATE INDEX idx_outbox_pending  ON outbox (aggregate_id, id) WHERE status = 'PENDING';

-- Serves the NOT EXISTS guard that stops a parked row being stepped over (FR-030). Tiny by
-- construction: a healthy system has zero rows here.
CREATE INDEX idx_outbox_parked   ON outbox (aggregate_id, id) WHERE status = 'PARKED';
```

| Column | Type | Serves | Notes |
|---|---|---|---|
| `id` | BIGINT identity | FR-014 | The recording sequence. Ordering is defined by this, not by `created_at` — see the caveat below. |
| `aggregate_id` | UUID | FR-008 | The order the message concerns. Also the Kafka partition key (FR-018), so ordering in the table and ordering on the channel come from the same value. |
| `event_type` | VARCHAR(64) | FR-008 | The channel name from `Topics`, e.g. `order.created`. Storing the channel rather than a class name means the relay never maps types to destinations at send time. |
| `payload` | JSONB | FR-010 | The message, serialized once at recording time and sent verbatim. `jsonb` normalises key order and whitespace — accepted, see R7. |
| `traceparent` / `tracestate` | VARCHAR | FR-025 | W3C Trace Context, captured at recording time. Stored as row fields, never inside `payload`, so the frozen contracts stay free of observability concerns. |
| `status` | VARCHAR(16) + CHECK | FR-029 | `PENDING` → `PUBLISHED` or `PENDING` → `PARKED`. Authoritative. |
| `attempts` | INTEGER | FR-028 | Incremented on every failed send. Reaching the configured limit is what parks the row. |
| `last_error` | TEXT | FR-028 | Why the most recent attempt failed, so a parked row explains itself without a log search. |
| `published_at` | TIMESTAMPTZ | FR-008 | Non-null exactly when `status = 'PUBLISHED'`, enforced by a CHECK rather than by convention. |

**Why both `status` and `published_at`.** The project brief's table used `published_at IS NULL` alone
to mean outstanding. That works for two states and cannot express a third, and parking needs a third.
`status` is therefore authoritative and `published_at` is kept as the *time* of publication; the CHECK
constraint stops the two drifting apart, which is the failure mode of carrying redundant state.

### State machine

```text
                          send succeeds
              ┌──────────────────────────────────►┌───────────┐
              │                                   │ PUBLISHED │  terminal
   ┌──────────┴──┐                                └───────────┘
   │   PENDING   │◄──┐ send fails, attempts < limit
   └──────────┬──┘   │ (attempts++, last_error set)
              │      └──────────────────────────┐
              │                                 │
              └────────────────────────────────►┴──►┌────────┐
                        send fails,                 │ PARKED │  terminal without a human
                        attempts = limit            └────────┘
```

A `PARKED` row halts every later row for the same `aggregate_id` (FR-030). That is deliberate: sending
past it would break per-order ordering, and an order whose saga cannot proceed is an incident, which
is why `outbox.records.parked` is a metric (R12).

## A caveat worth knowing: identity order is not commit order

`GENERATED AS IDENTITY` hands out values when a row is *inserted*, but rows become visible when their
transaction *commits*. Two concurrent inserts can therefore commit in the opposite order to their
ids, and a relay reading `MIN(id)` among visible rows could publish the later one first.

This system is not exposed to that, because an order advances one saga step at a time and each step
is driven by exactly one consumed message — so two outbox rows for the same `aggregate_id` are never
written concurrently. The risk is recorded here rather than left implicit, so that a later step which
introduces concurrent writes for one order recognises the cost instead of meeting it as an
intermittent ordering bug. If that day comes, the fix is a per-aggregate advisory lock held across
the insert, evaluated and rejected for today's needs in R2.

## Validation rules

Applied before anything is written (FR-005), each naming the offending field in an RFC 7807 response.

| Field | Rule | Source |
|---|---|---|
| `userId` | present, well-formed UUID | FR-005 |
| `showId` | present, well-formed UUID | FR-005 |
| `seatIds` | non-empty, no duplicates, each ≤ 32 characters | FR-005; duplicates also blocked by the `order_seats` primary key |
| `amount` | present, ≥ 0, scale exactly 2 | FR-005; matches the money rule frozen in step 1 |

Seat and show existence are **not** validated. This service has no catalogue; `inventory-service`
owns that truth and rejects what it cannot honour, from step 3.

## Mapping to the `OrderCreated` contract

The payload written to the outbox is a `common-events` `OrderCreated` record, serialized by this
service's `ObjectMapper` (R7). The mapping is total — every contract field has a source.

| `OrderCreated` field | Source |
|---|---|
| `messageId` | freshly generated UUID, unique per message; the consumer's idempotency key in step 3 |
| `sagaId` | `orders.id` — the contract's compact constructor asserts `sagaId == orderId` |
| `occurredAt` | the instant the order was accepted |
| `schemaVersion` | `1` |
| `orderId` | `orders.id` |
| `userId` | `orders.user_id` |
| `showId` | `orders.show_id` |
| `seatIds` | `order_seats.seat_id`, sorted for a deterministic payload |
| `amount` | `orders.amount` |
